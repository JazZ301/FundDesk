# 检查更新与自动更新方案

更新于 2026-11-28。状态：已接入手动检查更新与 GitHub Release 发布流程；自动检查与镜像加速尚未实现。

发布实操 skill 和 `v1.0.1` 耗时复盘见 `AI_HANDOFF.md`「发布 Skill」章节。特别注意：macOS updater
`.app.tar.gz` 内的 `CFBundleShortVersionString` 必须等于 Release 版本；只校验 `.sig` 和 `latest.json`
不足以证明更新包正确。`v1.0.1` 已替换错误归档，公开资产与真机升级均已复验通过。

## 结论

**不需要自备服务器，可以用 GitHub 免费实现。**

FundDesk 的安装包已经发布在公开仓库 `JazZ301/FundDesk` 的 GitHub Release 中。
Tauri 2 的 updater 支持直接读取 Release 里的静态 `latest.json`，安装包和更新包也由
GitHub 的 Release 资产托管。客户端只访问两个地址：

```text
https://github.com/JazZ301/FundDesk/releases/latest/download/latest.json
https://github.com/JazZ301/FundDesk/releases/download/<tag>/<更新包>
```

不需要域名、云主机、对象存储或数据库。GitHub 会返回 302 到具体版本资产，Tauri 的
HTTP 客户端会跟随重定向。

推荐直接做「应用内检查 + 下载安装 + 重启」的完整更新，而不是只弹窗让用户手动去
Release 页面下载。两者在 GitHub 上的托管方式相同，完整更新只多出签名密钥和一段
客户端状态机，但用户体验差别很大。

## 当前实现

- 设置页左侧已拆成「关于」和「免责声明」两个独立入口。「关于」页显示版本号和「检查更新」，检查后可显示版本、发布日期、说明、下载安装、进度和重启按钮。
- 已接入 `tauri-plugin-updater`、签名公钥、`requireSignedVersion` 和 Windows `passive` 安装模式。
- 已生成 minisign 密钥；私钥位于 `~/.tauri/funddesk.key`，不在仓库中；公钥写入 `src-tauri/tauri.conf.json`。
- 已新增 `.github/workflows/release.yml`：由 `v*` tag 触发，校验 tag 与版本一致，双平台构建，并把签名包和 `latest.json` 上传为 draft Release；单平台失败不再阻断另一平台产物上传，且至少一个 bundle job 必须成功。
- 日常构建工作流 `build.yml` 使用 `tauri.ci.conf.json` 关闭 updater 产物，避免未配置私钥时构建失败。
- 本机 macOS 构建脚本自动使用 `~/.tauri/funddesk.key` 签名，并把 `.app.tar.gz` 与 `.sig` 复制到 `release/`。
- GitHub Secrets 已配置；`v1.0.1` Release 已发布，公开 `latest.json` 已生效，应用内检查可发现 `1.0.1`。首次安装 `v1.0.0` 仍会显示「暂时没有可用的更新清单」，属于预期兼容状态。

## 两种实现级别

| 方案 | 客户端行为 | 需要签名密钥 | 适用阶段 |
| --- | --- | --- | --- |
| A. 只检查 | 读取清单，提示有新版本，打开发布页 | 不需要 | 临时验证、最低成本 |
| B. 应用内更新 | 检查、显示说明、下载、校验、安装、重启 | 需要 minisign | 推荐，面向真实用户 |

建议采用 B。当前 `1.0.0` 没有内置 updater，因此 `1.0.0` 用户必须先手动安装一次
`1.0.1`；从 `1.0.1` 起才能自动收到后续版本。这个一次性的手动升级无法追溯补上。

## GitHub 免费边界

公开仓库下：

- 标准 GitHub Actions runner 免费，公共仓库不受 2,000 分钟私有额度限制。
- 单个 Release 资产上限 2 GiB，单个 Release 最多 1,000 个资产。
- GitHub 文档明确说明 Release 没有总大小限制，也没有带宽限制。
- 公开仓库的 Release 资产可以匿名下载，不需要 token 或登录。
- `releases/latest` 只指向正式 Release，不包含 draft 和 prerelease。

因此当前约 12.5 MB 的 DMG、约 3 MB 的 NSIS 安装包完全在免费范围内。

必须注意：**私有仓库的 Release 资产下载需要认证**，把 token 放进客户端等于公开
token，不可接受。若仓库改为私有，就需要另找公开镜像或自建服务。当前仓库是公开的，
所以可以继续用 GitHub。

## 整体架构

```text
开发者推送 v1.0.1 tag
        │
        ▼
GitHub Actions（测试 → macOS universal + Windows x64 构建）
        │  minisign 私钥签名更新包
        ▼
GitHub Release v1.0.1
  ├─ FundDesk-1.0.1-macOS-universal.dmg
  ├─ FundDesk-1.0.1-Windows-x64-setup.exe
  ├─ FundDesk-1.0.1-macOS-universal.app.tar.gz
  ├─ FundDesk-1.0.1-macOS-universal.app.tar.gz.sig
  ├─ FundDesk-1.0.1-Windows-x64-setup.exe.sig
  └─ latest.json
        │
        ▼
已安装的 FundDesk
  GET releases/latest/download/latest.json
  → 比较版本
  → 下载对应平台的更新包
  → 用内置公钥校验 minisign
  → 安装并重启
```

## 清单格式

`latest.json` 由发布流程生成，至少包含：

```json
{
  "version": "1.0.1",
  "notes": "修复……；新增……",
  "pub_date": "2026-12-01T10:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "signature": "<.app.tar.gz.sig 的内容>",
      "url": "https://github.com/JazZ301/FundDesk/releases/download/v1.0.1/FundDesk-1.0.1-macOS-universal.app.tar.gz"
    },
    "darwin-x86_64": {
      "signature": "<同一个 .sig 的内容>",
      "url": "https://github.com/JazZ301/FundDesk/releases/download/v1.0.1/FundDesk-1.0.1-macOS-universal.app.tar.gz"
    },
    "windows-x86_64": {
      "signature": "<.exe.sig 的内容>",
      "url": "https://github.com/JazZ301/FundDesk/releases/download/v1.0.1/FundDesk-1.0.1-Windows-x64-setup.exe"
    }
  }
}
```

要点：

- `signature` 必须是 `.sig` 文件的完整内容，不是路径或 URL。
- macOS universal 包要在 `darwin-aarch64` 和 `darwin-x86_64` 两个键下指向同一个
  `.app.tar.gz`。Tauri 在 Apple Silicon 上查前者，在 Intel 上查后者；只写
  `darwin-universal` 时默认检查会找不到目标。
- 每个平台条目都必须同时有 `url` 和 `signature`。Tauri 会先校验整个文件，再比较
  版本；某一条不完整会让整份清单失效。
- `version` 用 SemVer，`1.0.1` 或 `v1.0.1` 都可，建议与 tag 一样不带 `v`。
- `notes` 按纯文本渲染，不要当 HTML 插入，避免更新说明成为注入入口。

## Tauri 配置

### 依赖

```toml
# src-tauri/Cargo.toml
tauri-plugin-updater = "2"
tauri-plugin-process = "2"
```

```json
// package.json
"@tauri-apps/plugin-updater": "^2",
"@tauri-apps/plugin-process": "^2"
```

### `tauri.conf.json`

```json
{
  "bundle": {
    "createUpdaterArtifacts": true,
    "macOS": {
      "minimumSystemVersion": "12.0",
      "signingIdentity": "-"
    }
  },
  "plugins": {
    "updater": {
      "pubkey": "<funddesk.key.pub 的内容>",
      "endpoints": [
        "https://github.com/JazZ301/FundDesk/releases/latest/download/latest.json"
      ],
      "windows": {
        "installMode": "passive"
      },
      "requireSignedVersion": true
    }
  }
}
```

说明：

- `createUpdaterArtifacts: true` 才会生成 macOS 的 `.app.tar.gz` 和 Windows 安装包的
  `.sig`。Windows 使用 NSIS 安装包本身作为更新包，不需要额外 zip。
- `signingIdentity: "-"` 表示 ad-hoc 签名，保证打包阶段生成的 `.app.tar.gz` 里的
  App 已经带有签名。当前本机脚本是在 Tauri 构建完成后再手动 `codesign`，这与
  updater 归档的生成顺序冲突，详见「签名顺序陷阱」。
- `APPLE_SIGNING_IDENTITY` 环境变量会覆盖这里的配置；将来配置 Developer ID 时，
  在 CI 或本机设置该变量即可，不需要改回配置文件。
- `requireSignedVersion` 让插件检查签名里记录的版本是否与清单一致，防止有人只改
  `latest.json` 的版本号、把旧签名包伪装成新版本。首次接入时所有更新包都由新 CLI
  签名，可以立即开启。该能力需要 Tauri CLI 2.12 及以上；当前锁定的 2.12.6 满足，
  但不要把 CLI 降级到旧版本。
- `installMode: "passive"` 在 Windows 上显示一个小的安装进度窗口，不需要用户一路
  点下一步；`currentUser` 安装模式不需要管理员权限。

### `lib.rs` 与权限

在 Tauri builder 中注册 updater 和 process 插件；capabilities 增加：

```json
{
```


## 客户端设计

### 入口

放在「设置 → 关于」内；「免责声明」是设置页独立的另一个入口：

```text
基金看板  1.0.0
[检查更新]
```

不建议单独增加一个只有按钮的设置标签；当前五个标签已经足够，关于页是用户寻找版本
信息的自然位置。可以把左侧导航的「关于与免责声明」副标题改为「版本与免责声明」。

### 状态

```text
idle
  → checking
      → up-to-date
      → available(version, notes, size)
          → downloading(progress)
              → installing
                  → restart-pending
              → error
      → error
```

界面文案：

- 检查中：「正在检查更新…」
- 已最新：「已是最新版本 · 刚刚检查」
- 有新版本：「发现 1.0.1，发布于 2026-12-01」+ 更新说明 + 更新包大小
- 下载中：「正在下载 38% · 4.7 MB / 12.3 MB」
- 安装中：「正在安装，完成后需要重启」
- 完成：「更新已安装」+「立即重启」/「稍后」
- 失败：「检查失败，请稍后重试」+「打开发布页」

失败时保留当前版本和当前数据，不进入半更新状态。

### 自动检查

- 启动后延迟 8 秒检查一次，避免和首屏行情、净值请求抢带宽。
- 默认每 24 小时最多自动检查一次，手动检查不受限制。
- 自动检查只提示，不自动下载，不打断用户操作。
- 开发模式、CI 和 QA 可用环境变量或 `import.meta.env.DEV` 关闭，避免测试时访问
  外网。
- 「自动检查更新」开关可放在同一张卡片，首版用 `localStorage` 保存即可；以后若希望
  跟看板设置一起备份，再迁到 Rust 的 `settings`。

### 更新说明

- 从 `latest.json` 的 `notes` 读取，按纯文本显示，保留换行。
- 长说明折叠，默认显示前 6 行。
- 提供「打开发布页」作为备用路径，便于签名校验失败或安装失败时手动下载。

### 数据安全

- 更新只替换应用包，不触碰 `~/Library/Application Support/FundDeskDesktop` 或
  `%APPDATA%\FundDeskDesktop` 下的 `board.json`、缓存和备份。
- 安装前如果正在保存看板，等当前写盘结束再安装；现有保存是临时文件 + 原子替换，
  即使进程被重启，最坏也是保留上一次完整版本。
- 「稍后重启」时不要再次提示；下次启动自然使用新版本。

## 签名与密钥

更新包使用 Tauri 的 minisign 签名，与 Apple Developer ID、Windows Authenticode
是两套独立机制。

一次性生成：

```sh
pnpm tauri signer generate -w ~/.tauri/funddesk.key
```

会得到：

- `~/.tauri/funddesk.key`：私钥，只放在本机安全位置和 GitHub Actions Secret。
- `~/.tauri/funddesk.key.pub`：公钥，写入 `tauri.conf.json` 的 `pubkey`，可以公开。

GitHub Secrets：

| Secret | 内容 |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | 私钥文件内容 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成密钥时设置的密码；未设置密码则留空 |

注意事项：

- 私钥一旦丢失，已安装用户无法再验证新更新，只能让用户手动重装。至少要有一份离线
  备份，不要只存在 CI Secret 里。
- 私钥不能进 Git，不能打进安装包，不能写进 `latest.json`。
- GitHub 账号或 Release 被篡改时，攻击者没有私钥仍无法生成可通过校验的更新包；但
  已经能改仓库的人也可能改 CI 读取 Secret，因此仍要保护仓库和 Actions 权限。
- 公钥更换等同于更换更新信任链，旧版本无法平滑升级到新公钥；不要随意轮换。

## 发布流程

当前 `.github/workflows/build.yml` 只构建并上传 Actions artifact，不创建 Release。
建议新增 `.github/workflows/release.yml`，由 tag 触发，保留现有 `build.yml` 作为
日常构建检查。

发布工作流必须使用 Tauri CLI 2.12 及以上，才能把版本写进签名并配合
`requireSignedVersion`；如果 CI 缓存或 `pnpm-lock.yaml` 回退到旧 CLI，需要先升级。

### 版本号

三处必须同步：

- `package.json`
- `src-tauri/Cargo.toml`
- `src-tauri/tauri.conf.json`

建议增加 `scripts/bump-version.sh`，一次改完三处并提示更新 `Cargo.lock`。Tauri
updater 读取的是打包进应用的 `tauri.conf.json` 版本，三处不一致会导致界面显示的
版本和实际比较版本不一致。

### 发布步骤

1. 修改版本号到 `1.0.1`。
2. 写 `release-notes/v1.0.1.md`，同时作为 GitHub Release 正文和 `latest.json` 的
   `notes`。
3. 提交并推送 `main`，确认 `build.yml` 通过。
4. 打 tag 并推送：

   ```sh
   git tag v1.0.1
   git push origin v1.0.1
   ```

5. `release.yml` 运行测试，分别构建 macOS universal 和 Windows x64。
6. 两个平台都用 `TAURI_SIGNING_PRIVATE_KEY` 生成 `.sig`。
7. 创建/更新 GitHub Release，上传安装包、更新包、`.sig` 和 `latest.json`。
8. 从干净环境实际下载 `latest.json`，确认 URL 可访问、签名长度正确。
9. 用上一版本安装包做一次真实升级，确认版本号、数据和界面。

### `tauri-action` 配置要点

`tauri-apps/tauri-action` 已支持多平台共同写入一个 Release，并自动生成
`latest.json`。关键参数：

```yaml
permissions:
  contents: write

env:
  TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
  TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
with:
  tagName: v__VERSION__
  releaseName: FundDesk v__VERSION__
  releaseDraft: true
  uploadUpdaterJson: true
  updaterJsonPreferNsis: true
```

`tauri-action` 需要 `contents: write` 才能创建 Release 和上传资产，并需要
`GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`。Release 工作流只由 `v*` tag 触发，
不要在每个 `main` 提交上创建版本。

先把 Release 设为 draft，两个平台都上传完成后再手动发布，可以避免 Windows 用户先
看到一个还没有 macOS 资产的版本。`updaterJsonPreferNsis: true` 保证 Windows 使用
NSIS 安装包而不是 MSI。

`releases/latest` 不包含 draft 和 prerelease。可以用 `v1.0.1-rc.1` 做预发布测试，
但测试时要把端点临时指向该 tag 的 `latest.json`，或直接使用 `--config` 覆盖端点，
不能依赖 `releases/latest`。

### 签名顺序陷阱

当前 `scripts/build-macos-dmg.sh` 的流程是：

1. `pnpm tauri build --bundles app`
2. 脚本再对 `.app` 执行 `codesign`
3. 手工生成 DMG

接入 `createUpdaterArtifacts` 后，Tauri 在第 1 步就会生成 `.app.tar.gz`，此时脚本
还没执行第 2 步。结果可能是：DMG 里的 App 已签名，但 updater 归档里的 App 未签名，
Apple Silicon 上更新后无法启动。

处理方式二选一：

- 推荐：在 `tauri.conf.json` 设置 `bundle.macOS.signingIdentity: "-"`，让 Tauri 在
  打包阶段完成 ad-hoc 签名，再生成 updater 归档；脚本不再重复签名，或只做校验。
- 或者：脚本在手动签名后重新生成 `.app.tar.gz`，再用
  `pnpm tauri signer sign` 重新生成 `.sig`。这种方式容易漏步骤，不如前者稳。

本机脚本和 CI 必须使用同一种顺序，否则会出现「本机测试能更新、CI 发布不能更新」
或相反的问题。

## 平台差异

### macOS

- 当前是 ad-hoc 签名，未公证。首次从 DMG 安装仍会被 Gatekeeper 拦截，需要右键打开
  或在「隐私与安全性」中允许；这不是 updater 能解决的。
- Tauri updater 安装阶段只做 minisign 校验和 App 替换，不校验 Apple 签名；更新包
  解开后没有 quarantine 属性，通常可以启动。但 ad-hoc 签名每次构建都会变化，仍需
  在 Apple Silicon 和 Intel 上各做一次真实升级验证。
- App 在 `/Applications` 且当前用户有写权限时可直接替换；否则会弹出管理员授权。
  如果用户从 DMG 直接运行，更新只会替换 DMG 挂载卷或下载目录里的副本，建议在关于页
  提示「请将 App 移到 Applications」。
- 长期公开分发仍建议配置 Developer ID + 公证；这是安装信任问题，不影响 GitHub
  托管更新的可行性。

### Windows

- NSIS 按用户安装，更新不需要管理员权限。
- `passive` 模式会显示安装进度窗口；安装器默认会重启应用，客户端不要重复调用
  `relaunch`，以实际插件行为为准做一次验证。
- 未做 Authenticode 签名时，首次安装仍可能触发 SmartScreen；自动更新包由
  minisign 校验，不受 SmartScreen 对 exe 的首次下载提示影响。
- 更新前确认 NSIS 安装目录与旧版本一致，否则会出现新旧两个副本。

## 失败与回滚

- 清单 404：视为「暂无更新」，不要报错。首次接入、Release 尚未发布时都会遇到。
- 网络超时/断网：自动检查静默失败；手动检查显示可重试提示。
- 下载中断：丢弃临时文件，下次重新下载；不要安装不完整包。
- 签名不匹配：拒绝安装，保留旧版本，提示打开发布页。
- macOS 替换失败：插件会尽量把旧 App 放回原位，并在无法恢复时保留
  「基金看板 (previous version).app」。需要在实机验证这条路径。
- 坏版本：不要删除旧 Release；发布更高的修复版本（如 `1.0.2`）。默认禁止降级，
  不能把 `1.0.1` 用户“更新”回 `1.0.0`；紧急情况下让用户手动重装。
- `latest.json` 指向错误平台：先发布一个仅修正清单的补丁版本，或直接替换 Release
  资产；替换资产后注意 CDN 缓存，使用 tag 固定 URL 比 `latest/download` 更可控。

## 中国网络环境

本机实测从 GitHub Release 拉取 1 MiB 的平均速度约 280 KB/s，12.5 MB 的包约 45 秒。
这对更新可以接受，但不同地区、不同运营商差异很大。

建议先把 GitHub 作为唯一来源上线，观察真实用户失败率。如果大量用户下载失败或速度
低于 100 KB/s，再增加镜像：

- Cloudflare R2：免费额度 10 GB 存储，出站流量免费；需要自定义域名，仍然不需要
  自己维护服务器。
- 其它对象存储或国内 CDN：把 `latest.json` 里的 `url` 指向镜像即可，客户端逻辑
  不变。

注意 Tauri 只有在端点返回非 2xx 时才会尝试下一个端点，单纯「GitHub 很慢」不会自动
切换。因此镜像方案应直接把清单里的下载 URL 换成镜像，而不是并列两个端点。
